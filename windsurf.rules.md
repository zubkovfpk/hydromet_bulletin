# Правила AI-правок для репозитория

## 1) Секреты и чувствительные данные

- AI **нельзя редактировать** файлы, содержащие секреты или потенциально содержащие секреты (например: `config.ini`, `.env`).
- AI может **только читать** такие файлы **для понимания структуры** (ключи/секции/формат), без копирования/логирования содержимого секретов.
- AI **нельзя предлагать реальные SMTP-пароли**.

## 2) Что считать конфигами проекта

- Конфигами проекта считаются:
  - `config.example.ini`
  - `config.ini`

## 3) Что считать рабочими данными

- Рабочими данными считаются любые файлы и каталоги в:
  - `data/*`
  - `output/*`
  - `logs/*`

AI не должен изменять/перезаписывать рабочие данные без явного запроса.

## 4) Где находится кодовая логика проекта

- Ключевая кодовая логика проекта находится в:
  - `forecast_*.py`
  - `utils/`
  - `scripts/`

Изменения логики следует выполнять преимущественно в этих местах.

## 5) Любые изменения секретов — только через пользователя

- Любые изменения секретов (значения токенов, паролей, ключей, приватных URL и т.п.) выполняются **только через пользователя**.
- AI **не предлагает реальные значения** секретов и **не подставляет** их в код/конфиги.
- Если для работы требуются значения секретов, AI:
  - описывает, **какие именно** значения нужны (названия ключей/переменных),
  - просит пользователя предоставить их безопасным способом,
  - или просит пользователя внести их вручную.

---

## 6) Слой загрузки данных: файлы, которые Windsurf может свободно создавать и изменять

В рамках реализации `data ingestion` слоя (см. `docs/data_ingestion_design.md`) Windsurf **может свободно создавать и изменять**:

- `fetch_inputs.py` — новый entry point слоя загрузки (создаётся с нуля);
- `utils/downloaders/__init__.py` — новый пакет (создаётся с нуля);
- `utils/downloaders/cmems_downloader.py` — новый модуль загрузки CMEMS (создаётся с нуля);
- `utils/downloaders/gfs_downloader.py` — новый модуль загрузки GFS (создаётся с нуля);
- любые новые файлы в `docs/` (дизайн-документы, описания, схемы);
- любые новые тестовые файлы (`tests/`, `test_*.py`).

Принцип: **только аддитивные изменения** — новые файлы/модули, не меняющие существующих интерфейсов.

---

## 7) Файлы, которые можно менять только после явного запроса пользователя

Следующие файлы являются операционным контуром проекта. Windsurf **не трогает их без явного запроса**:

- `forecast_morning.py` — основной сценарий утреннего бюллетеня;
- `forecast_evening.py` — основной сценарий вечернего бюллетеня;
- `scripts/deploy.sh`, `scripts/install.sh`, `scripts/run_now.sh`, `scripts/status.sh`, `scripts/stop.sh`, `scripts/logs.sh`, `scripts/update.sh` — точки входа Docker/cron;
- `Dockerfile` — образ контейнера;
- `docker-compose.yml` — оркестрация сервисов;
- `crontab` — расписание запусков;
- `utils/collect_wave_data.py`, `utils/collect_meteo_data.py` — ядро расчётов волн и метео;
- `utils/wind_statistics.py`, `utils/precip_statistics.py`, `utils/temp_statistics.py` — статистические модули;
- `utils/doc_builder.py`, `utils/email_sender.py` — сборка документа и рассылка.

Если изменение этих файлов всё же необходимо — Windsurf **описывает намерение и ждёт подтверждения** перед правкой.

---

## 8) Файлы, строго запрещённые к изменению и коммиту

Windsurf **никогда не изменяет и не добавляет в коммит** следующие файлы:

- `config.ini` — рабочий конфиг с секретами. **Изменение допускается только после явного кнопочного подтверждения** (интерактивная форма «Да» / «Нет» перед каждой командой). Явная инструкция «исправить `config.ini`» в тексте сообщения **не является разрешением** — разрешение только нажатая кнопка **Да**. При отказе — описать что нужно внести вручную. В коммит не добавлять.
- `.env` — переменные окружения с секретами (только чтение структуры);
- `data/*` — реальные рабочие данные (входные файлы, кеши, маркеры);
- `etalon_data/*` — эталонные данные для проверки качества;
- `output/*` — сформированные бюллетени и артефакты;
- `logs/*` — лог-файлы рабочих запусков;
- любые файлы `*.doc`, `*.docx` — описания, шаблоны, согласованные документы.

---

## 9) Стартовые правила для AI-агента

При начале **каждой** сессии AI-агент **обязан** прочитать следующие файлы **до** любых правок:

1. `docs/project_context.md` — единственный canonical source of truth по контексту проекта (архитектура, статус, решения, process rules).
2. `docs/conversation_history.md` — история сессий, reasoning и согласованных решений.

Если агент не прочитал эти файлы — он не имеет актуального контекста и **не должен** вносить изменения в код или документацию.

Файл `project_context.md` в любом другом месте репозитория (например, в корне) **не актуален** и должен игнорироваться.

---

## 10) Branch discipline

- Feature-работа ведётся **только** в `feature/*`-ветках, **не в `master`**.
- Текущий активный этап (`validate_outputs.py`, bulletin generation) — ветка `feature/bulletin-generation`.
- Прямые feature-коммиты в `master` **запрещены**.
- `docs:`, `chore:`, `fix:`-коммиты без незавершённого feature-кода допустимы в `master`.
- Merge в `master` только через `git merge --no-ff` после явного согласования с пользователем.
